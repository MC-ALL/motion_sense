# 02 — 器材端

## 定位

安装于健身器材（跑步机、力量训练机、椭圆机等）上，承担**双重角色**：

1. **本地传感器节点**：采集器材运行状态（轴位、动作计数）与能耗数据。
2. **BLE 中枢节点（BLE Central）**：主动扫描并连接附近手环，聚合手环数据后与器材自身数据一并通过 WiFi/MQTT 上报至网关。

网关**无需** BLE 硬件，所有 BLE 接入工作由器材端完成。

---

## 1. 数据获取

### 1.1 采集数据类型

| 数据类型 | 传感器类型 | 字段 | 采样周期 |
|---------|-----------|------|---------|
| 瞬时功率 | 功率传感器 | `power_w`（W） | 100 ms |
| 累计能耗 | 功率传感器积分 | `energy_wh`（Wh） | 持续累加 |
| 供电电压 | 功率传感器 | `voltage_v`（V） | 100 ms |
| 供电电流 | 功率传感器 | `current_ma`（mA） | 100 ms |
| 轴位角度 | 旋转编码器 | `axis_angle`（0.1°） | 中断驱动 |
| 动作计数 | 旋转编码器推算 | `rep_count`（次） | 中断驱动 |
| 器材状态 | 逻辑推断 | `status`（空闲/使用中/异常） | 实时更新 |

### 1.2 智能计数逻辑

动作计数基于编码器轴位变化推算：

```
编码器中断 → 轴位变化检测：
  1. 检测轴位完成一次完整运动周期（峰值到谷值往返）
  2. 过零检测 + 防抖（连续多次采样确认，避免抖动误计）
  3. 计数 +1，触发提示音
  4. 计数达到目标次数 → 长提示音 + 上报 MQTT alert
```

### 1.3 能耗计算

```
功率传感器每 100ms 采样：
  电压 × 电流 → 瞬时功率 P（W）
  累计能耗 E += P × Δt（Wh，积分累加，重启后从 0 开始）
```

### 1.4 器材状态判断

| 状态 | 判断条件 |
|------|---------|
| `idle`（空闲） | 轴位无变化且功率 < 待机阈值，持续 30 s |
| `active`（使用中） | 有编码器中断或功率 > 待机阈值 |
| `error`（异常） | 功率 > 额定功率 × 150% 或传感器读取失败 |

## 2. 数据上传

### 2.1 器材自身数据

器材端直连 MQTT Broker，每 500 ms 上报一次：

**Topic：** `gym/{gym_id}/equipment/{device_id}/telemetry`

字段定义见 [07-通讯接口定义.md §2.3](./07-通讯接口定义.md)。

上报周期可由云端通过 `config` 动态调整，见第 4 节。

### 2.2 手环转发数据

器材端收到手环 BLE Notify 后，解析 Payload 并立即转发至 MQTT：

**Topic：** `gym/{gym_id}/wristband/{wristband_id}/telemetry`

转发帧额外附加 `relayed_by`（器材端 device_id）和 `current_equipment_id` 字段，供后台关联手环与器材的绑定关系。字段定义见 [07-通讯接口定义.md §2.3](./07-通讯接口定义.md)。

### 2.3 MQTT 订阅

器材端同时订阅以下 topic，接收下行指令：

| Topic | 用途 |
|-------|------|
| `gym/{gym_id}/equipment/{device_id}/config` | 动态配置下发（阈值、周期、目标次数） |
| `gym/{gym_id}/equipment/{device_id}/ota` | OTA 固件升级触发 |

### 2.4 连接可靠性

- MQTT QoS 1，确保消息送达
- WiFi 或 MQTT 断线后自动重连，重连期间 BLE 连接不受影响
- 重连成功后 MQTT 消息从断点恢复发布

## 3. BLE Central 功能（手环接入）

### 3.1 器材端 BLE 角色

| BLE 层 | 器材端角色 | 说明 |
|--------|-----------|------|
| GAP | **Central** | 主动扫描，发现广播中的手环后发起连接 |
| GATT | **Client** | 订阅手环 Notify，向手环写入时间/器材 ID/配置 |

### 3.2 手环识别与绑定

器材端通过广播包中的 Manufacturer Specific Data 快速识别手环：

- `Device Type = 0x01`：确认为手环
- `Device ID`：与本地授权列表比对，只连接授权手环

连接成功后，器材端向手环写入自身 `equipment_id`（通过 EQUIPMENT_ID Characteristic），实现手环与器材的动态绑定。后台通过手环上报数据中的 `current_equipment_id` 字段得知绑定关系。

绑定完成后，器材端向 MQTT 发布 `binding` 事件（action=bind），后台记录绑定历史。

### 3.3 解绑机制

解绑由器材端主动触发，有以下两种情形：

**情形 A：BLE 连接断开（手环离开范围）**

```
BLE 断开事件（gap_disconnect callback）
  → 器材端立即发布 MQTT binding 事件（action=unbind，reason=ble_disconnected）
  → 重置内部绑定状态
  → 重新开始扫描，等待手环重连
```

**情形 B：空闲超时（用户停止使用但手环仍在范围内）**

```
检测条件：编码器无中断 + 功率降至待机阈值，持续 5 min
  → 器材端通过 WRISTBAND_CMD 向手环发送"解绑"指令
    （cmd_type=0x04，param1=0x00）
  → 手环将 current_equipment_id 重置为 0xFF
  → 器材端发布 MQTT binding 事件（action=unbind，reason=idle_timeout）
  → 器材端等待手环重新靠近时再次绑定
```

**解绑后手环状态：** `current_equipment_id = 0xFF`（未绑定），后续 Notify 帧携带此值，后台据此标记会话结束。

MQTT binding 事件格式见 [07-通讯接口定义.md §2.5](./07-通讯接口定义.md)。

### 3.4 多手环并发

- 器材端可同时维持多条 BLE 连接（受 MCU RAM 限制，建议 ≤ 4 条）
- 每条连接独立处理 Notify 回调，分别转发至对应的 MQTT wristband topic
- 手环间数据互不干扰

## 4. 配置持久化与时间同步

### 4.1 时间同步

器材端通过 WiFi 获取准确时间，并同步至手环：

```
WiFi 连接成功
  → SNTP 同步（从 NTP 服务器获取 Unix 时间戳）
  → 每 60 分钟重新同步（防止时钟漂移）

BLE 连接手环后
  → 写入 TIME_SYNC Characteristic（UUID: 0xFFA3，4 bytes，uint32 LE）
  → 手环更新本地计时基准

手环 Notify 中 ts = 0（手环未同步）
  → 器材端用本地时间替换后再转发 MQTT
```

### 4.2 配置持久化

器材端需持久化以下配置（断电重启后保持有效）：

| 配置项 | 默认值 | 来源 |
|--------|--------|------|
| `notify_interval_ms` | 500 ms | 云端 config 下发 |
| `target_reps` | 0（不限制） | 云端 config 下发 |
| `power_limit_w` | 额定功率 × 150% | 云端 config 下发 |
| WiFi SSID / 密码 | 出厂烧录 | 本地配置 |
| `equipment_id` | 出厂烧录 | 本地配置 |
| `gym_id` | 出厂烧录 | 本地配置 |

云端配置变更通过“后台配置命令 -> 网关轮询 -> 局域网 MQTT `config` topic”链路下发，格式见 [07-通讯接口定义.md §2.7](./07-通讯接口定义.md)。

## 5. 与手环连接流程

器材端作为 BLE Central，主动扫描并连接手环。

### 5.1 连接参数

| 参数 | 值 |
|------|-----|
| 扫描模式 | 被动扫描（不发送 Scan Request） |
| 连接间隔 | 100 ms |
| 最大并发连接 | ≤ 4 条（视 MCU RAM 而定） |

### 5.2 连接建立步骤

```
1. 开机初始化
   WiFi 连接 → SNTP 时间同步 → BLE 初始化 → 开始扫描

2. 扫描阶段
   收到广播包 → 解析 Manufacturer Specific Data
   Device Type = 0x01 且 Device ID 在授权列表中
   → 停止扫描，发起连接请求

3. 连接建立
   Link Layer 连接参数协商 → ATT MTU 协商（默认 23 bytes）
   → GATT Service Discovery，发现 Service UUID 0xFFA0

4. 订阅 Notify
   写入 WRISTBAND_DATA CCCD = 0x0001
   → 手环开始每 notify_interval_ms 发送 Notify

5. 时间同步
   写入 TIME_SYNC Characteristic（0xFFA3）当前 Unix 时间戳

6. 器材绑定
   写入 EQUIPMENT_ID Characteristic（0xFFA4）
   包含 equipment_id（1 byte）+ equipment_name（7 bytes ASCII）
   → 手环存储并在后续 Notify 中携带 current_equipment_id

7. 正常数据传输
   收到手环 Notify → 解析 20-byte Payload
   → 补填 ts（若手环 ts=0）、relayed_by、current_equipment_id
   → MQTT Publish 至 wristband telemetry topic
```

### 5.3 断线处理

- BLE 连接断开后，器材端立即重新开始扫描
- 重连成功后，重复步骤 4–6（时间同步 + 绑定 ID 重写）
- 重连期间，器材自身数据继续正常上报，不受 BLE 状态影响

## 6. 与网关连接流程

器材端通过 WiFi 连接网关上的 MQTT Broker。

### 6.1 连接步骤

```
1. WiFi Station 模式连接路由器（SSID/密码出厂烧录）
2. SNTP 时间同步
3. MQTT 连接 Broker（broker_ip:1883，Client ID = equipment_id）
4. 订阅 config 和 ota topic
5. 开始周期发布 equipment telemetry
6. 同时开启 BLE 扫描，接入手环后转发 wristband telemetry
```

### 6.2 掉线重连策略

| 事件 | 处理 |
|------|------|
| WiFi 断线 | 自动重连，指数退避（1 s → 2 s → 4 s，最长 30 s） |
| MQTT 断线 | 自动重连，重连后重新订阅 config / ota topic |
| BLE 断线 | 独立处理，不影响 WiFi/MQTT，重新扫描并连接 |
