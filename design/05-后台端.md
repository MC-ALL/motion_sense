# 05 — 后台端

## 定位

云端服务，接收并持久化来自网关的全量数据，提供用户管理、设备管理、历史查询 REST API，通过 WebSocket 向前端推送实时数据与告警。业务后台不再承担基础设施健康汇聚职责，相关能力将拆分到独立 `ops_observer`。

---

## 技术栈

| 层次 | 选型 |
|------|------|
| Web 框架 | FastAPI（Python 异步框架，原生 WebSocket） |
| 关系型数据库 | PostgreSQL（用户、设备、告警等结构化数据） |
| 时序数据库 | TimescaleDB（PostgreSQL 扩展，传感器时序数据） |
| 缓存 / 消息 | Redis（实时状态缓存，WebSocket 跨进程广播） |
| 配置命令中转 | FastAPI + 异步存储队列（后台仅暴露 REST / WebSocket） |
| AI 分析 | 内置规则生成器 + OpenAI 兼容外部模型（默认 `reasoner` 档位映射到 `deepseek-reasoner`） |
| 认证 | JWT + scrypt（refresh session 已落地到存储层，支持进程重建后继续轮换） |
| 部署 | Docker Compose（网页端通过 Nginx 单端口同源代理访问后台） |

---

## 主要功能

### 1. 数据接入

后台通过内网 HTTP 接口接收网关批量上传的数据：

- `POST /api/v1/ingest/batch`
- 上报批次包含 `telemetry`、`alert`、`binding`、`status`
- 收到批次后：解析 JSON → 写入 TimescaleDB / PostgreSQL → Redis Pub/Sub → WebSocket 广播前端

### 1.1 时间语义与接入约束

- 网关上传的 `payload.ts` / `ts` 字段表示设备原始时间戳，后台入库时不得改写。
- 后台可追加 `backend_received_at` 作为入库时间，用于链路追踪和后续分析。
- 当前主接入链路仍是 `POST /api/v1/ingest/batch`，RTOS 设备端不直接调用后台 REST API。

### 1.2 自观测接口（当前已实现）

后台对 `ops_observer` 暴露自身健康与统计接口，供运维端通过 REST / WebSocket 拉取或订阅：

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/ops/v1/health` | 返回后台整体健康摘要 |
| GET | `/ops/v1/health/components` | 返回 API、数据库、Redis 等组件状态 |
| GET | `/ops/v1/stats` | 返回入库速率、WebSocket 连接数、命令执行统计等 |
| WS | `/ops/ws` | 推送后台运行状态变化 |

**当前实现边界：**

- 当前已实现：`GET /ops/v1/health`、`GET /ops/v1/health/components`、`GET /ops/v1/stats`、`WS /ops/ws`
- 最新设计中，业务后台不再向网页端直接提供基础设施健康汇总
- 网关与后台基础设施健康统一由 `ops_observer` 对外汇聚，业务后台不再保留 `/api/v1/system/health/*` 兼容路由

### 2. 数据持久化

**PostgreSQL（结构化数据）：**

| 表 | 内容 |
|----|------|
| `users` | 用户账户、角色 |
| `user_wristband_bindings` | 学生账号与手环 device_id 的绑定关系 |
| `devices` | 设备注册信息、在线状态 |
| `alerts` | 告警记录（含 priority P0/P1）、确认状态 |
| `ai_reports` | AI 分析报告存档 |
| `equipment_binding_events` | 手环-器材绑定历史（见下） |
| `workout_sessions` | 训练会话聚合结果与器材分段摘要 |
| `device_config_commands` | 设备配置命令、执行状态与结果 |

**`equipment_binding_events` 表结构：**

```sql
equipment_binding_events (
  id          SERIAL PRIMARY KEY,
  wristband_id TEXT NOT NULL,        -- 手环 device_id
  equipment_id TEXT NOT NULL,        -- 器材 device_id
  gym_id       TEXT NOT NULL,
  action       TEXT NOT NULL,        -- 'bind' | 'unbind'
  reason       TEXT,                 -- 'ble_connected' | 'ble_disconnected' | 'idle_timeout'
  ts           TIMESTAMPTZ NOT NULL, -- 事件发生时间（来自 MQTT binding 消息）
  duration_s   INTEGER               -- 仅 unbind 行填写：本次使用时长（秒）
);
CREATE INDEX ON equipment_binding_events (wristband_id, ts DESC);
CREATE INDEX ON equipment_binding_events (equipment_id, ts DESC);
```

**`user_wristband_bindings` 表结构：**

```sql
user_wristband_bindings (
  id          BIGSERIAL PRIMARY KEY,
  username    TEXT NOT NULL,
  wristband_id TEXT NOT NULL,
  gym_id      TEXT NOT NULL,
  is_active   BOOLEAN NOT NULL DEFAULT TRUE,
  bound_at    TIMESTAMPTZ NOT NULL,
  unbound_at  TIMESTAMPTZ,
  source      TEXT NOT NULL DEFAULT 'manual',
  note        TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON user_wristband_bindings (username, is_active, bound_at DESC);
CREATE INDEX ON user_wristband_bindings (wristband_id, is_active, bound_at DESC);
```

约束：
- 同一 `username` 当前只能保留 1 条 `is_active = true` 的手环绑定。
- 同一 `wristband_id` 当前也只能绑定到 1 个用户。
- 当前写接口收敛为后台管理员维护；教师 / 学生只读。

**`workout_sessions` 表结构：**

```sql
workout_sessions (
  session_id    UUID PRIMARY KEY,
  username      TEXT NOT NULL,
  wristband_id  TEXT NOT NULL,
  gym_id        TEXT NOT NULL,
  status        TEXT NOT NULL,       -- open | completed | cancelled
  source        TEXT NOT NULL,       -- manual | imported | aggregated
  started_at    TIMESTAMPTZ NOT NULL,
  ended_at      TIMESTAMPTZ,
  duration_s    INTEGER,
  equipment_ids JSONB NOT NULL,      -- ["eq-001", "eq-002"]
  segments      JSONB NOT NULL,      -- 分段器材摘要
  metrics       JSONB NOT NULL,      -- 心率/动作/能耗等聚合指标
  notes         TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON workout_sessions (username, started_at DESC);
CREATE INDEX ON workout_sessions (wristband_id, started_at DESC);
```

当前定位：
- 当前已落地“训练会话结果存储与查询接口”，并补齐基于器材绑定解绑事件的自动汇聚 MVP。
- `segments` 用于记录单次训练中不同器材段落；`metrics` 用于沉淀 AI 报告、学生训练档案与统计页的直接输入。

**写入时机：** 后台处理网关上传的 `binding` 事件后：
- `action=bind`：插入一行，`duration_s = NULL`
- `action=unbind`：插入一行，同时查找最近一次同 wristband + equipment 的 bind 记录，计算 `duration_s = unbind.ts - bind.ts`
- 同步更新 `devices` 表中的手环快照：`bind` 将设备状态设为 `bound`，`unbind` 恢复为 `online`
- 当收到 `action=unbind` 时，后台会在近 6 小时窗口内按“同一学生-手环关系 + 器材分段间隔不超过 15 分钟”自动汇聚训练会话，并回填 `workout_sessions`
- 管理员也可通过 `POST /api/v1/workout-sessions/aggregate` 对指定 `username` / `wristband_id` / `gym_id` 范围执行手动回填，适合历史数据补算或联调排障

**TimescaleDB（时序数据，Hypertable 按 ts 分区）：**

| 表 | 内容 |
|----|------|
| `wristband_telemetry` | 心率、加速度、陀螺仪、步数、电量、当前绑定器材 |
| `equipment_telemetry` | 功率、能耗、轴位、动作计数 |
| `env_telemetry` | 温湿度、光照、CO₂、PM2.5/PM10 |

### 3. 实时推送

WebSocket 端点（`/api/ws`）向前端推送：

- **telemetry**：后台收到网关批量上传的新数据后即时广播
- **alert**：告警产生后即时推送所有已连接客户端（含 P0/P1 优先级字段）
- **device_status**：设备上下线变更

多进程广播通过 Redis Pub/Sub 实现，连接管理器维护 `user_id → WebSocket[]` 映射。

### 3.1 首次初始化与重启规则

- `api_service` 首次启动时从镜像内 `default_app_settings.yaml` 生成运行时配置文件
- `app_settings.yaml` 变更后需要重启 `api_service`
- Redis 配置变更后需要重启 `redis`
- TimescaleDB 镜像、初始化 SQL、持久化卷参数变更后需要重启 `timescaledb`
- 运行时不使用 `.env`；部署参数由编排层直接注入容器环境变量

### 4. AI 运动分析

用户触发「生成报告」后：

1. 训练档案页或其他前端入口提交 `user_id / start / end`
2. 后台按分析窗口查询该学生的 `workout_sessions`，并收集证据会话 ID
3. 创建 `queued` 报告记录，并回填 `evidence_session_ids`
4. 后台 AI 处理服务在建单 / 重试后立即入队异步消费 `queued` 记录，并在服务启动时恢复遗留的 `queued / generating` 报告
5. 若部署启用 `ai.wakeup_backend=redis`，建单 / 重试实例会向 Redis 唤醒 channel 广播 `report_id`，其他实例收到后同步入队，避免多实例下仅本地 worker 被唤醒
6. 真正开始生成前，后台会以原子方式把报告从 `queued` 抢占到 `generating`，避免多实例重复消费同一条报告
7. 默认使用内置规则化生成器基于训练会话摘要生成中文 `summary`、`insights`、`recommendations` 与 `raw_markdown`
8. 若部署配置为 `openai_compatible`，则改走 OpenAI 兼容接口调用外部模型；接口路径仍为 `POST /chat/completions`
9. 报告完成后更新 `ai_reports` 表，状态推进到 `completed` 或 `failed`

**外部模型接入方式：** 当前已落地 OpenAI 兼容配置，默认模板使用 `base_url="https://api.deepseek.com/v1"`、`model_variant="reasoner"`、`model=null`；未配置 `api_key` 时，后台继续使用内置规则化生成器离线完成报告。

**token 存放建议：**

- 不要把外部模型 `api_key` 直接写进 Git 管理的 YAML、Compose 文件或源码
- 当前项目默认从宿主机 `deployment/runtime/secrets/backend_ai_api_key.txt` 读取 AI token
- 也可通过 `BACKEND_AI_API_KEY_FILE` 改写读取路径；若显式设置 `BACKEND_AI_API_KEY`，其优先级更高
- 推荐宿主机权限：
  - 文件属主为部署用户
  - 文件权限 `600`
  - 所在目录 `deployment/runtime/secrets/` 权限按敏感目录管理
- Linux Compose 下可通过 `sh deployment/compose/write_backend_ai_api_key.sh` 交互写入 token 文件
- 如已运行中的栈需要切换到 `openai_compatible`，修改 `deployment/runtime/config/backend/api_service/app_settings.yaml` 后需重启 `backend_api_service`
- Linux Compose 下可通过 `sh deployment/compose/switch_backend_ai_model.sh reasoner|chat` 一条命令切换 `ai.model_variant` 并自动重启 `backend_api_service`
- 可通过 `sh deployment/compose/verify_ai_stack.sh` 验证“训练会话自动汇聚 -> AI 报告完成 -> 网页 AI 报告详情路由”整条链路
- 日常推荐通过 `ai.model_variant` 在 `reasoner` 与 `chat` 之间切换；仅在确有需要时再直接写 `ai.model`
- 调用路径仍为 OpenAI 兼容的 `POST /chat/completions`；`deepseek-reasoner` 是模型名，不是另一条 REST 路径
- 当前已统一使用中文 system/user 提示词，要求模型返回中文 `summary_title`、`summary`、`insights`、`recommendations` 与 `raw_markdown`
- 当模型为 `deepseek-reasoner` 时，请求体不再发送 `temperature`，避免触发 provider 参数校验错误

**当前落地边界：**

- 已接入接口位置：`POST /api/v1/ai/analyze`、`GET /api/v1/ai/reports`、`GET /api/v1/ai/reports/{id}`、`POST /api/v1/ai/reports/{id}/retry`
- 当前已实现 JWT 登录、刷新与退出；部署默认开启强制鉴权，网关采集与命令通道 / pending 兜底 / 结果回报这类内网接口按链路免 JWT 放行
- 当前已实现 `ai_reports` 基础存储：`POST /api/v1/ai/analyze` 会创建一条 `queued` 报告记录，并回填训练窗口内的 `evidence_session_ids`
- 当前 `GET /api/v1/ai/reports`、`GET /api/v1/ai/reports/{id}` 已返回真实数据库记录，供网页端列表页 / 详情页直接消费
- 当前 `POST /api/v1/ai/reports/{id}/retry` 已支持对 `failed / completed` 报告按原分析窗口重新创建一条新的 `queued` 记录，作为“重新生成 / 再次生成”的最小任务编排基础
- 当前后台已新增自动 AI 处理服务：默认将报告从 `queued` 推进到 `generating -> completed/failed`，并生成摘要、观察结论、建议与 `raw_markdown`
- 当前 AI worker 已改为“建单 / 重试即入队 + 服务启动恢复”，不再依赖固定周期扫库触发生成
- 当前已支持 `ai.wakeup_backend=redis` 的多实例唤醒模式：建单 / 重试后会通过 Redis channel 广播 `report_id`，并以原子 `queued -> generating` 抢占避免重复生成
- 当前未接入流式输出；网页端当前通过“首次 REST 加载 + 业务 WebSocket `ai_report` 事件”观察状态推进。外部大模型调用已完成 OpenAI 兼容接入与 Linux Compose 实测，默认闭环仍可在离线环境下工作

### 4.1 OTA 任务预留

当前 OTA 仅预留后台接口，不做实际任务编排：

- `POST /api/v1/devices/{id}/ota`
- `GET /api/v1/ota/tasks`
- `GET /api/v1/ota/tasks/{task_id}`

当前 OTA 路由仍统一返回 `501 reserved`，用于前后端先对齐接口位置。设备侧与网关侧升级机制暂未实现。
该部分当前**不纳入后续开发排期**。

### 5. 设备配置云控

后台可向任意设备下发配置，但**不直接连接 MQTT Broker**。当前链路统一为：

1. 后台接收 `POST /api/v1/devices/{id}/config`
2. 后台创建待执行命令并持久化
3. 若目标网关在线，后台通过 `WS /api/v1/gateway/{gateway_id}/commands/ws?token=...` 推送 `command_ready`
4. 网关收到通知后立即拉取 `GET /api/v1/gateway/{gateway_id}/commands/pending`；若长连接不可用则继续周期轮询兜底
5. 网关执行本地配置，或转发到局域网 MQTT `gym/{gym_id}/{device_type}/{device_id}/config`
6. 网关通过 `POST /api/v1/gateway/{gateway_id}/commands/{command_id}/result` 回报结果

**当前结果语义：**

- `gateway` 目标：`succeeded` 表示网关本地配置已写入运行时文件
- `wristband / equipment / env` 目标：`succeeded` 仅表示网关已成功发布到局域网 MQTT
- 设备侧当前**没有预留 ACK 机制**，后台不能据此认定设备已持久化配置
- 命令状态机当前为：`pending`、`succeeded`、`failed`、`timed_out`
- 网关每次拉取待执行命令时，后台会为命令增加 `attempt_count` 并设置短期 `leased_until`
- 网关回报 `failed` 后，如未超过 `max_attempts` 且未达到 `expires_at`，后台会按 `retry_backoff_s` 重新排队
- 超过最大尝试次数后命令结束为 `failed`；超过有效期后命令结束为 `timed_out`

| 目标 | 可配置项 |
|------|---------|
| 手环 | 心率告警上下阈值、Notify 周期 |
| 器材端 | 上报周期、目标次数 |
| 环境端 | 上报周期、各环境告警阈值 |
| 网关 Edge Processor | P1 告警规则（阈值、持续时间窗口） |

配置格式见 [07-通讯接口定义.md §2.7](./07-通讯接口定义.md)。

### 默认鉴权边界（第 1 迭代当前实现）

- 部署默认配置已开启 `auth.enforce_rest = true`、`auth.enforce_ws = true`
- 以下内网接口继续保持免 JWT，供网关与模块间调用：
  - `POST /api/v1/ingest/batch`
  - `WS /api/v1/gateway/{gateway_id}/commands/ws?token={gateway_channel_token}`

  - `POST /api/v1/gateway/{gateway_id}/commands/{command_id}/result`
- 以下接口默认要求 `Authorization: Bearer {access_token}`：
  - 设备、告警、历史遥测、绑定历史、配置命令详情
  - 后台自观测 `GET /ops/v1/*`
- 以下 WebSocket 默认要求 `token={access_token}`：
  - `/api/ws`
  - `/ops/ws`

### 当前实现路由结构（第 1 迭代）

后台应用当前在代码中按以下顺序挂载路由：

1. `/healthz`：健康检查
2. `/api/v1/ingest/*`：网关批量入库
3. `/api/v1/auth/*`：JWT 登录、刷新、退出
4. `/api/v1/devices/*`：设备查询、设备详情、配置下发
5. `/api/v1/ota/*`：OTA 任务占位接口
6. `/api/v1/alerts/*`：告警查询、确认、批量确认
7. `/api/v1/telemetry/*`：手环 / 器材 / 环境历史查询与环境聚合
8. `/api/v1/wristband/*`：手环绑定历史
9. `/api/v1/user-wristband-bindings/*`：学生-手环绑定关系与设备管理页绑定概览
10. `/api/v1/workout-sessions/*`：训练会话摘要
11. `/api/v1/users/{username}/training-profile`：训练档案聚合视图
12. `/api/v1/gateway/*`：配置命令 WebSocket、pending 兜底与结果回报
13. `/api/v1/ai/*`：AI 报告创建、列表与详情查询
14. `/api/ws`：实时 WebSocket 推送
15. `/ops/v1/*`、`/ops/ws`：后台自观测接口

当前主数据流为：

1. 网关调用 `POST /api/v1/ingest/batch`
2. 后台解析批次并写入 TimescaleDB / PostgreSQL
3. 写入成功后通过 WebSocket 向前端推送
4. 多实例场景下可通过 Redis Pub/Sub 实现跨进程广播
5. 配置下发通过 `POST /api/v1/devices/{id}/config` 入库为待执行命令
6. 在线网关通过 `WS /api/v1/gateway/{gateway_id}/commands/ws?token=...` 收到 `command_ready`，随后调用 `GET /api/v1/gateway/{gateway_id}/commands/pending` 拉取命令并在本地执行 / 转发 MQTT
7. 若命令长连接暂时不可用，网关仍按固定轮询间隔调用 `commands/pending` 作为兜底
8. 网关调用 `POST /api/v1/gateway/{gateway_id}/commands/{command_id}/result` 回报执行结果
9. 基础设施健康汇聚职责已从业务后台设计中拆分，后续由 `ops_observer` 统一聚合网关与后台状态
10. 学生账号与手环绑定关系由管理员维护，训练会话摘要可独立查询，为后续自动聚合与 AI 分析提供稳定输入
11. 训练档案聚合接口当前直接组合用户、绑定和训练会话数据，供网页端统一展示“某学生近期练了什么、结果如何”

### 4. 配置命令与 MQTT 验证边界

当前第 1 迭代后台主接入链路不是直接订阅设备 MQTT，而是接收网关 HTTP 批量上报。

因此后台侧验证分两部分：
- 网关侧验证 MQTT 是否成功进入 `POST /api/v1/ingest/batch`
- 后台侧验证 REST 入库、历史查询、WebSocket 广播，以及配置命令推送 / pending 兜底接口是否正确

设备配置云控当前已完成“后台建单 -> `command_ready` 推送 -> 网关补拉 pending -> 网关本地 MQTT 转发 / 本地应用 -> 结果回报”的基础闭环。若命令长连接中断，网关仍可依赖定时轮询恢复。由于设备侧当前未预留 ACK 机制，后台只知道“网关已本地执行”或“网关已成功转发 MQTT”，不能确认设备最终是否完成持久化。

### 5.1 运维观测边界

- `ops_observer` 只能通过后台暴露的 `/ops/v1/*` 与 `/ops/ws` 获取后台观测信息。
- 后台不向 `ops_observer` 暴露数据库私有连接串，也不要求 `ops_observer` 直连 PostgreSQL、Redis。
- 业务接口与运维接口分离，避免健康观测逻辑污染业务路由和数据权限。

## 权限与角色

| 角色 | 权限范围 |
|------|---------|
| 管理员 | 全部功能，含用户管理、设备注册、配置下发 |
| 教师 | 仪表盘、告警、AI 报告（全体学生）、只读设备配置 |

当前第 1 迭代已实现基础用户管理与角色登录：支持 `admin`、`teacher`、`student` 三种角色签发 JWT，并新增 `GET/POST/PATCH/DELETE /api/v1/users`。当前角色边界为：`admin` 负责用户管理、设备注册写操作、配置下发、学生-手环绑定维护、训练会话写入与运维健康查询；`teacher` 可读取 `gym_ids` 对应场馆下的业务数据，也可读取 `device_ids` 明确绑定的设备数据，并允许执行告警确认；`student` 仅可读取 `device_ids` 明确绑定的设备数据，但可额外读取 `username == 当前账号` 的个人手环绑定与训练会话摘要。业务 `WS /api/ws` 同样按 `gym_id` / `device_id` 做实时过滤。bootstrap admin 继续由部署配置托管，不允许通过用户管理接口改密、降权或删除。
