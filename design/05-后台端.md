# 05 — 后台端

## 文档定位

本文只描述后台模块的领域边界、核心数据模型、实时链路、AI 基线与权限模型。

不在本文中展开：
- 详细 REST / WebSocket 字段，见 [07-通讯接口定义.md](./07-通讯接口定义.md)
- 具体测试命令与部署方法，见 `backend/api_service/README.md`
- 上线、回滚、验收与运行手册，见 `deployment/compose/README.md`

## 1. 定位与职责

后台是云端业务服务，负责：
- 接收网关批量上报的数据并持久化
- 提供用户、设备、告警、训练档案与 AI 报告业务接口
- 通过业务 WebSocket 向网页端推送实时状态
- 承担配置命令持久化与命令中转
- 对外暴露自身自观测接口，供 `ops_observer` 汇聚

明确不做：
- 不再承担基础设施健康聚合，相关职责已拆到 `ops_observer`
- RTOS 设备端不直接调用后台 REST，设备接入主入口仍是网关

## 2. 技术栈

| 层次 | 选型 |
|------|------|
| Web 框架 | FastAPI |
| 关系数据 | PostgreSQL |
| 时序数据 | TimescaleDB |
| 缓存 / 广播 | Redis |
| 认证 | JWT + scrypt |
| AI | 内置规则生成器 + OpenAI 兼容外部模型 |
| 部署入口 | Docker Compose，同源代理由网页端 Nginx 提供 |

## 3. 核心数据模型

### 3.1 结构化数据

当前核心表：
- `users`
- `devices`
- `alerts`
- `equipment_binding_events`
- `user_wristband_bindings`
- `workout_sessions`
- `device_config_commands`
- `ai_reports`

### 3.2 时序数据

当前核心时序表：
- `wristband_telemetry`
- `equipment_telemetry`
- `env_telemetry`

### 3.3 训练档案相关模型

关键约束：
- 同一学生当前只能有 1 条激活手环绑定。
- 同一手环当前也只能绑定到 1 个学生。
- `workout_sessions` 存储训练会话摘要与分段信息，不承担原始遥测存储职责。

当前自动汇聚口径：
- 后台收到 `binding.unbind` 后，会在近 6 小时窗口内按“同一学生-手环关系 + 器材段间隔不超过 15 分钟”自动生成或更新训练会话。
- 管理员可通过聚合接口手动回填历史区间。

## 4. 接入与实时链路

### 4.1 数据接入

主接入路径：`POST /api/v1/ingest/batch`

当前处理流程：
1. 接收网关批次。
2. 解析并写入 PostgreSQL / TimescaleDB。
3. 更新设备、绑定、告警等快照。
4. 通过本地广播或 Redis Pub/Sub 把增量事件推送到业务 WebSocket。

### 4.2 实时广播

业务 WebSocket 为 `WS /api/ws`。

当前已稳定使用的事件类型包括：
- `telemetry`
- `alert`
- `device_status`
- `device_upsert`
- `device_delete`
- `binding_upsert`
- `binding_remove`
- `ai_report`

网页端当前采用：
- 首次 REST 加载
- WebSocket 增量更新
- WebSocket 重连后的单次 REST 补同步

## 5. AI 报告处理链路

### 5.1 当前链路

1. 前端调用 `POST /api/v1/ai/analyze`。
2. 后台按训练窗口查询 `workout_sessions`。
3. 创建 `queued` 报告记录，并写入 `evidence_session_ids`。
4. AI worker 抢占任务，状态推进到 `generating`。
5. 生成成功后写回 `summary_title`、`summary`、`insights`、`recommendations`、`raw_markdown`。
6. 完成后状态推进到 `completed` 或 `failed`，并通过 `ai_report` 事件广播。

### 5.2 当前实现边界

- 当前已支持 `queued -> generating -> completed/failed`。
- 当前已支持 `POST /api/v1/ai/reports/{id}/retry`，重新生成时会创建新的报告记录。
- 当前已支持多实例下基于 Redis 的唤醒广播与原子抢占，避免重复消费。
- 当前未实现流式正文输出；`ai_chunk` 仅保留契约位置。

### 5.3 外部模型接入

当前支持两条路径：
- `builtin`
- `openai_compatible`

运行约束：
- AI token 默认从 `deployment/runtime/secrets/backend_ai_api_key.txt` 读取。
- `model_variant` 当前支持 `reasoner | chat`。
- 调用路径仍是 OpenAI 兼容的 `POST /chat/completions`；`reasoner` 是模型档位，不是另一条 REST 路径。
- 当前 system / user 提示词已统一为中文。

## 6. 配置命令中转

后台负责：
- 持久化配置命令
- 以网关为粒度分发命令
- 维护命令状态、重试与有效期

当前闭环边界：
- 网关目标可确认“已执行”。
- 设备目标仅能确认“网关已转发到 MQTT”。
- 设备实际应用与持久化仍依赖后续设备 ACK 设计。

## 7. 权限模型

角色：
- `admin`
- `teacher`
- `student`

当前权限原则：
- `admin` 拥有全量范围。
- `teacher` 依据 `gym_ids`、`device_ids` 查看授权范围。
- `student` 仅查看本人及明确授权设备范围。
- 设备写操作、用户管理、手环绑定维护、训练会话回填、运维接口等仍以 `admin` 为主。

默认部署约束：
- REST 与 WebSocket 强制鉴权默认开启。
- 仅网关入库与命令通道相关接口保留内网免 JWT 放行。

## 8. 自观测接口

后台对 `ops_observer` 暴露：
- `GET /ops/v1/health`
- `GET /ops/v1/health/components`
- `GET /ops/v1/stats`
- `WS /ops/ws`

这些接口服务于运维聚合，不承担业务页面直接聚合职责。

## 9. 运行时约束

- 首次启动从默认模板生成正式配置。
- `app_settings.yaml` 修改后需要重启后台容器。
- Redis、TimescaleDB、JWT 参数与 AI provider 配置变更同样按重启生效。
- 全部运行时文件统一放在 `deployment/runtime/`。

## 10. 当前限制

- AI 仍是进程内 worker 基线，尚未演进为独立任务系统。
- AI 失败分类、超时恢复、人工接管流程仍需增强。
- OTA 接口仍为 `501 reserved`。
- 设备配置仍缺最终设备 ACK 闭环。

## 11. 后续计划

- 将 AI worker 继续演进为独立队列或独立进程。
- 细化 AI 失败恢复、重试策略与正式报告结构。
- 继续增强会话聚合、权限隔离和多实例集成验证。
