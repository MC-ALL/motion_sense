## 0. BLE 基础知识

> 本节面向对蓝牙协议不熟悉的开发者，介绍 BLE 的基本工作原理，帮助理解本项目的 BLE 设计。

### 0.1 BLE 是什么

BLE（Bluetooth Low Energy，低功耗蓝牙）是蓝牙 4.0 起引入的短距离无线协议，工作在 2.4 GHz ISM 频段，采用自适应跳频（FHSS），最大传输距离约 10～100 m（视功率和障碍物而定）。

与经典蓝牙（BR/EDR）相比，BLE 的核心优势是**极低功耗**——在广播状态下平均电流可低至数微安，非常适合电池供电的可穿戴设备。

---

### 0.2 BLE 协议层次

```
应用层（App）
    │
GATT（Generic Attribute Profile）—— 定义数据格式和读写方式
    │
ATT（Attribute Protocol）—————— 数据传输的基本单元（属性 Attribute）
    │
L2CAP（逻辑链路控制与适配）————— 数据分片/重组
    │
Link Layer（链路层）—————————— 连接管理、加密、跳频
    │
Physical Layer（物理层）—————— 2.4 GHz 无线射频，40 个信道
```

你在开发时主要与 **GATT** 和 **GAP** 两层打交道。

---

### 0.3 GAP 角色：谁主动，谁被动

**GAP（Generic Access Profile）** 定义了设备的发现和连接角色：

| 角色 | 行为 | 本项目对应 |
|------|------|-----------|
| **Peripheral（外设）** | 持续广播自身信息，等待别人连接 | **手环**（nRF5340 / ESP32-S3） |
| **Central（中心）** | 主动扫描，发现 Peripheral 后发起连接 | **器材端**（ESP32-S3） |
| Broadcaster | 只广播，不接受连接（单向广播） | 不使用 |
| Observer | 只扫描，不建立连接（只听广播） | 不使用 |

**广播（Advertising）：** Peripheral 每隔一定时间（广播间隔）在 3 个广播信道（37/38/39 频道）发送广播包（ADV_IND），包含设备名称、服务 UUID、厂商数据等信息。Central 扫描到广播包后，若满足条件则主动发起连接（CONNECT_IND）。

---

### 0.4 GATT 结构：数据如何组织

**GATT（Generic Attribute Profile）** 定义了 BLE 设备上数据的组织方式，采用层次结构：

```
GATT Server（数据提供方 = Peripheral = 手环）
  └── Profile（应用场景，如"健身手环"）
       └── Service（服务，一组相关功能）  ← 有 UUID 标识
            └── Characteristic（特征值，具体数据项） ← 有 UUID + Properties
                 ├── Value（实际数据，如心率数值）
                 └── Descriptor（描述符，如 CCCD 控制 Notify 开关）
```

**GATT Client（数据使用方 = Central = 器材端）** 连接后执行：
- **Service Discovery**：读取所有 Service 和 Characteristic 的 UUID 和属性
- **Read**：主动读取某个 Characteristic 的值
- **Write**：向某个 Characteristic 写入数据（如下发指令）
- **Subscribe Notify**：通过写 CCCD（Client Characteristic Configuration Descriptor）开启 Notify

---

### 0.5 UUID：服务和特征的地址

**UUID（Universally Unique Identifier）** 是 BLE 中每个 Service / Characteristic 的唯一标识。

- **16-bit Short UUID**（如 `0xFFA0`）：蓝牙 SIG 分配的标准 UUID，或厂商申请的自定义短 UUID，广播包和内存占用小
- **128-bit Full UUID**（如 `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`）：完全自定义，无需向 SIG 申请，但广播包体积更大

本项目使用 16-bit 自定义 UUID（`0xFFA0` 系列用于手环，`0xFFB0` 系列用于器材）。

---

### 0.6 Notify 机制：如何实时接收数据

BLE 有三种数据推送方式，本项目使用 **Notify**：

| 方式 | 方向 | 需要 Client 确认 | 适用场景 |
|------|------|-----------------|---------|
| Read | Client 主动读取 | — | 低频偶尔读取 |
| **Notify** | Server 主动推送（无确认） | 否 | **高频实时数据（心率/姿态）** |
| Indicate | Server 主动推送（需确认） | 是 | 重要告警（延迟可接受） |

**开启 Notify 的步骤：**
```
Client（器材端）找到 Characteristic UUID → 找到其 CCCD Descriptor
  → Write CCCD = 0x0001（开启 Notify）
  → Server（手环）开始每个 Notify 周期推送数据
  → Client 在 notify_callback 中接收数据
```

---

### 0.7 MTU：每帧能传多少字节

**MTU（Maximum Transmission Unit）** 决定每个 ATT 数据包的最大字节数：

| MTU | ATT 净荷（Payload） | 说明 |
|-----|---------------------|------|
| 23 bytes（默认） | **20 bytes** | BLE 4.x 默认，无需协商即可使用 |
| 最大 247 bytes | 244 bytes | BLE 4.2+ 支持协商，需双方都支持 |

本项目所有 Notify Payload 设计为 **固定 20 bytes**，兼容默认 MTU，不依赖协商。

---

### 0.8 本项目 BLE 拓扑总览

```
手环（GATT Server / Peripheral）
  │ 广播：Device Type=0x01，Service UUID=0xFFA0
  │ 连接后：每 100ms Notify WRISTBAND_DATA (0xFFA1)
  │ 接受：Write WRISTBAND_CMD (0xFFA2) / TIME_SYNC (0xFFA3)
  │
  │ BLE 5.0 GATT 连接（最大 ~10m，室内有效）
  ▼
器材端（GATT Client / Central）
  │ 扫描 → 发现手环广播 → 连接 → Service Discovery
  │ 写 CCCD → 订阅 Notify → 接收手环 20-byte Payload
  │ 解析后转为 JSON → MQTT Publish（转发手环数据）
  │ 同时采集自身 INA226 / 编码器 → MQTT Publish（器材数据）
  │
  │ MQTT over WiFi（QoS 1）
  ▼
网关 Mosquitto Broker（无 BLE，纯 MQTT）
  │
  ▼
后台 / 网页端
```

**一台器材端可同时连接多个手环**（NimBLE 多连接，受 ESP32-S3 RAM 限制，建议 ≤ 4 条并发 BLE 连接）。

## 1. BLE GATT 接口

### 1.1 公共约定

| 项目 | 约定 |
|------|------|
| BLE 版本 | BLE 5.0 |
| 最大 ATT MTU | 247 bytes（协商后） |
| Notify 帧大小 | ≤ 20 bytes（兼容默认 MTU） |
| 字节序 | **Little-Endian**（LSB first） |
| 时间戳（`ts`） | Unix 时间戳，秒级整数。**器材端**通过 NTP/SNTP 获取准确时间，连接手环后通过 TIME_SYNC Characteristic 写入手环。手环 ts=0 时由器材端补填本地时间。 |
| Central 角色 | **器材端**（ESP32-S3 NimBLE） |
| Peripheral 角色 | 手环端 |

---

### 1.2 手环端 GATT Service

**Service UUID：** `0xFFA0`（自定义 16-bit Short UUID）

#### Characteristic: WRISTBAND_DATA（上报）

| 字段 | UUID | Properties |
|------|------|------------|
| WRISTBAND_DATA | `0xFFA1` | Notify |

**Payload 结构（20 bytes，固定长度）：**

```
Byte    Field             Type    Unit       Description
───────────────────────────────────────────────────────────────
[0]     data_flags        uint8   —          bit0=姿态有效, bit1=心率有效, bit2=低电量
[1]     battery_pct       uint8   %          电池电量 0~100
[2-3]   heart_rate        uint16  bpm        心率，0 表示无效
[4-5]   step_count        uint16  步          本次连接累计步数
[6-7]   accel_x           int16   mg         X 轴加速度（1g = 1000 mg）
[8-9]   accel_y           int16   mg         Y 轴加速度
[10-11] accel_z           int16   mg         Z 轴加速度
[12-13] gyro_x            int16   0.1 °/s    X 轴角速度
[14-15] gyro_y            int16   0.1 °/s    Y 轴角速度
[16-17] gyro_z            int16   0.1 °/s    Z 轴角速度
[18]    current_eq_id     uint8   —          当前绑定的器材 ID（0xFF=未绑定）
[19]    reserved          uint8   —          保留，填 0x00
```

**Notify 周期：** 100 ms（运动中），1000 ms（静止超过 5 min）

---

#### Characteristic: WRISTBAND_CMD（下发）

| 字段 | UUID | Properties |
|------|------|------------|
| WRISTBAND_CMD | `0xFFA2` | Write Without Response |

**Payload 结构（4 bytes）：**

```
Byte  Field       Type    Description
────────────────────────────────────────────
[0]   cmd_type    uint8   0x01=震动, 0x02=蜂鸣, 0x03=显示文本, 0x04=解绑
[1]   param1      uint8   震动: 次数(1-10); 蜂鸣: 时长(ms/10); 解绑: 0x00
[2]   param2      uint8   保留
[3]   checksum    uint8   XOR([0], [1], [2])
```

**解绑指令（cmd_type=0x04）：** 手环收到后清除 `current_equipment_id`（置 0xFF），无需断开 BLE 连接。适用于用户停止使用器材但未离开 BLE 范围的场景。

#### Characteristic: TIME_SYNC（时间同步，器材端→手环）

| 字段 | UUID | Properties |
|------|------|------------|
| TIME_SYNC | `0xFFA3` | Write |

**Payload 结构（4 bytes）：**

```
Byte  Field       Type    Description
──────────────────────────────────────────────
[0-3] unix_ts     uint32  Unix 时间戳（秒），Little-Endian
                          器材端连接手环后立即写入
```

手环收到后更新本地计时基准，后续 WRISTBAND_DATA Notify 中的 `ts` 字段以此为准。

---

#### Characteristic: EQUIPMENT_ID（器材绑定，器材端→手环）

| 字段 | UUID | Properties |
|------|------|------------|
| EQUIPMENT_ID | `0xFFA4` | Write |

**Payload 结构（8 bytes）：**

```
Byte  Field           Type    Description
──────────────────────────────────────────────────────
[0]   equipment_id    uint8   器材编号（0~255）
[1-7] equipment_name  char[7] 器材名称（ASCII，不足补0x00）
                              如 "TM-01\0\0"（跑步机01）
```

**用途：** 器材端连接手环后写入自身 ID 和名称，手环可：
- 在本地显示当前操作的器材（如有屏幕）
- 在 WRISTBAND_DATA Notify 中携带 `current_equipment_id` 字段
- 后台通过此字段关联"哪个手环正在操作哪台器材"

---

### 1.3 器材端 GATT Service

**Service UUID：** `0xFFB0`（自定义 16-bit Short UUID）

#### Characteristic: EQUIPMENT_DATA（上报）

| 字段 | UUID | Properties |
|------|------|------------|
| EQUIPMENT_DATA | `0xFFB1` | Notify |

**Payload 结构（20 bytes，固定长度）：**

```
Byte    Field              Type    Unit        Description
────────────────────────────────────────────────────────────────
[0]     equipment_id       uint8   —           器材编号 0~255（现场写入配置）
[1]     status             uint8   —           0=空闲, 1=使用中, 2=异常, 3=离线
[2-3]   rep_count          uint16  次            本组累计重复次数
[4-5]   power_w            uint16  W           当前瞬时功率（0~65535 W）
[6-9]   energy_wh_x100     uint32  Wh×100      累计能耗（÷100 得 Wh）
[10-11] axis_angle         int16   0.1 °       当前轴位角度（−1800 ~ +1800）
[12-13] voltage_v_x10      uint16  V×10        供电电压（÷10 得 V）
[14-15] current_ma         uint16  mA          电流（0~65535 mA）
[16-19] reserved           uint32  —           保留，填 0x00000000
```

**Notify 周期：** 500 ms（使用中），5000 ms（空闲）

---

#### Characteristic: EQUIPMENT_CONFIG（下发）

| 字段 | UUID | Properties |
|------|------|------------|
| EQUIPMENT_CONFIG | `0xFFB2` | Write |

**Payload 结构（6 bytes）：**

```
Byte  Field           Type    Description
────────────────────────────────────────────────
[0]   config_type     uint8   0x01=设置目标次数, 0x02=清零计数, 0x03=重启
[1-2] target_reps     uint16  目标重复次数（config_type=0x01 时有效）
[3-5] reserved        uint24  保留，填 0
```

---

### 1.4 BLE 广播包格式

所有 Peripheral 在广播包 Manufacturer Specific Data 中携带以下结构，供 Central 快速识别类型，无需建立连接：

```
AD Type 0xFF (Manufacturer Specific Data):
  Byte [0-1] : Company ID = 0xFFFF（测试用，正式产品向 Bluetooth SIG 申请）
  Byte [2]   : Device Type  0x01=手环, 0x02=器材
  Byte [3]   : Device ID (0~255，现场配置)
  Byte [4]   : 状态字节（手环=电量%, 器材=status 枚举）
```

## 2. MQTT 接口

### 2.1 公共约定

| 项目 | 约定 |
|------|------|
| Broker 地址 | 网关树莓派内网 IP（或云端 Broker） |
| 端口 | 1883（内网明文），8883（TLS） |
| QoS | 遥测数据 QoS 1，告警 QoS 1，配置下发 QoS 1 |
| Retained | 设备状态 topic 设 `retain=true`，遥测数据 `retain=false` |
| Payload 格式 | **JSON UTF-8**，无多余空白 |
| 时间戳字段 | `ts`：Unix 时间戳（秒，整数），由上报设备填入，需 NTP 同步 |

**当前接入认证方式：**

| 项目 | 当前约定 |
|------|------|
| 认证方式 | MQTT 用户名 + 密码 |
| 匿名访问 | 禁止（`allow_anonymous false`） |
| 开发默认用户名 | `admin` |
| 开发默认密码 | `admin123` |
| 正式部署 | 必须替换默认口令，并按设备或设备组收紧 ACL |
| ACL 基线 | 当前开发环境允许认证用户读写 `gym/#`；正式环境需改为最小权限 |

**TLS 说明：**

| 项目 | 约定 |
|------|------|
| 开发联调 | 默认使用 `1883` 明文内网端口 |
| 生产加固 | 推荐启用 `8883` + TLS |
| 证书材料 | `ca.crt`、`server.crt`、`server.key` 由部署阶段提供，不提交代码库 |

**RTOS 设备端最小 MQTT 参数模板：**

```c
mqtt_client_config_t cfg = {
  .broker_host = "<gateway_ip>",
  .broker_port = 1883,
  .username = "admin",
  .password = "admin123",
  .client_id = "<device_id>",
  .qos = 1,
  .keepalive_s = 60,
  .clean_session = true,
};
```

**字段说明：**
- `broker_host`：网关 MQTT Broker 内网 IP
- `broker_port`：开发联调使用 `1883`；启用 TLS 后改为 `8883`
- `username` / `password`：由部署阶段分发；上面的 `admin` / `admin123` 仅限当前本地开发默认值
- `client_id`：建议直接使用设备唯一 ID，如 `eq-001`、`env-zone-a`
- `qos`：当前约定统一为 `1`
- `keepalive_s`：建议 `60`
- `clean_session`：建议 `true`；若后续要做离线消息恢复，再单独评估持久会话

**时间语义约定：**

- MQTT 消息体中的 `ts` 表示设备原始时间戳，进入网关、后台后不得覆盖。
- 网关或后台可补充辅助字段 `gateway_received_ts`、`backend_received_at`，但不得回写到 `ts`。
- 规则判断与统计默认以 `payload_ts` 为准，并预留统一枚举：`payload_ts`、`gateway_received_ts`、`backend_received_at`。

```
gym/{gym_id}/{device_type}/{device_id}/{action}

```

### 2.3 遥测数据（telemetry）

#### 手环端

**Topic：** `gym/{gym_id}/wristband/{device_id}/telemetry`  
**方向：** **器材端**（BLE Central）收到手环 Notify → 解析 Payload → MQTT Publish 至 Broker  
**周期：** 100 ms

```json
{
  "ts": 1712345678,
  "device_id": "wb-001",
  "heart_rate": 142,
  "step_count": 2340,
  "battery_pct": 78,
  "accel": { "x": 120, "y": -980, "z": 150 },
  "gyro":  { "x": 5,   "y": -2,   "z": 1   },
  "flags": 3,
  "current_equipment_id": 1,
  "relayed_by": "eq-001"
}
```

**字段说明：**
- `current_equipment_id`：手环当前绑定的器材 ID（255 表示未绑定）
- `relayed_by`：转发此消息的器材端 device_id

#### 器材端

**Topic：** `gym/{gym_id}/equipment/{device_id}/telemetry`  
**方向：** 器材端直连 MQTT → Broker  
**周期：** 500 ms（使用中）

```json
{
  "ts": 1712345678,
  "device_id": "eq-001",
  "status": "active",
  "rep_count": 12,
  "power_w": 350.5,
  "energy_wh": 1.25,
  "axis_angle": 45.5,
  "voltage_v": 220.3,
  "current_ma": 1592
}
```

#### 环境端

**Topic：** `gym/{gym_id}/env/{node_id}/telemetry`  
**方向：** 环境端 → Broker  
**周期：** 30 s

```json
{
  "ts": 1712345678,
  "node_id": "env-zone-a",
  "temperature": 26.5,
  "humidity": 65.2,
  "lux": 380.0,
  "co2_ppm": 850,
  "pm1_0": 12,
  "pm2_5": 18,
  "pm10": 25,
  "wifi_rssi": -62
}
```

### 2.4 告警（alert）

**Topic：** `gym/{gym_id}/{device_type}/{device_id}/alert`  
**方向：** 设备端 / 网关 → Broker（即时触发）

```json
{
  "ts": 1712345678,
  "device_id": "wb-001",
  "priority": "P0",
  "level": "critical",
  "code": "HR_HIGH",
  "message": "心率过高：182 bpm，持续 35 s",
  "value": 182,
  "threshold": 180
}
```

**告警优先级（priority）：**

| 值 | 含义 | 处理位置 | 示例 |
|----|------|---------|------|
| `P0` | 生命安全，需立即本地处理 | **设备端本地判断并告警** | 心率异常、跌倒检测 |
| `P1` | 低风险，需关注但非紧急 | **网关边缘处理** | 器材过载、环境超标、设备离线 |

**告警级别（level）：**

| 值 | 含义 |
|----|------|
| `info` | 提示 |
| `warning` | 需关注 |
| `critical` | 需立即处理 |

**告警码（code）枚举：**

| Code | Priority | 触发端 | 含义 |
|------|----------|--------|------|
| `HR_HIGH` | **P0** | 手环本地 | 心率超阈值（手环立即震动） |
| `HR_LOW` | **P0** | 手环本地 | 心率过低（< 40 bpm） |
| `FALL_DETECTED` | **P0** | 手环本地 | 跌倒检测（加速度突变） |
| `BATTERY_LOW` | P1 | 手环 | 电量低于 10% |
| `EQ_OVERLOAD` | P1 | 网关 | 器材功率超额定 150% |
| `CO2_HIGH` | P1 | 网关 | CO₂ > 1000 ppm |
| `PM25_HIGH` | P1 | 网关 | PM2.5 > 75 µg/m³ |
| `TEMP_HIGH` | P1 | 网关 | 温度 > 35 °C |
| `DEVICE_OFFLINE` | P1 | 网关 | 设备心跳丢失超 30 s |

### 2.5 绑定事件（binding）

**Topic：** `gym/{gym_id}/wristband/{wristband_id}/binding`  
**方向：** 器材端 → Broker（绑定或解绑时触发）  
**QoS：** 1

```json
{
  "ts": 1712345678,
  "wristband_id": "wb-001",
  "equipment_id": "eq-001",
  "gym_id": "gym-gz-01",
  "action": "bind",
  "reason": "ble_connected"
}
```

**action 枚举：**

| 值 | 含义 | 触发时机 |
|----|------|---------|
| `bind` | 手环与器材绑定 | BLE 连接成功 + EQUIPMENT_ID 写入完成后 |
| `unbind` | 手环与器材解绑 | BLE 断开 或 空闲超时 |

**reason 枚举：**

| 值 | 含义 |
|----|------|
| `ble_connected` | BLE 连接建立（绑定时） |
| `ble_disconnected` | BLE 连接断开（手环离开范围） |
| `idle_timeout` | 空闲超时（用户停止使用，BLE 仍连接） |

后台收到 `binding` 事件后：
1. 写入 `equipment_binding_events` 表记录绑定历史
2. 计算 bind→unbind 的时间差，得到本次使用时长
3. 更新设备实时状态，通过 WebSocket 推送前端

### 2.7 配置下发（config）

**Topic：** `gym/{gym_id}/{device_type}/{device_id}/config`  
**方向：** 网关 → 设备端  
**QoS：** 1（确保送达）

**后台配置命令链路：**

1. 后台或网页端调用 `POST /devices/{device_id}/config`
2. 后台生成待执行命令，记录目标 `gateway_id`
3. 网关调用 `GET /gateway/{gateway_id}/commands/pending` 拉取命令
4. 若目标为当前网关，则本地应用配置；否则转发到对应 MQTT `config` topic
5. 网关调用 `POST /gateway/{gateway_id}/commands/{command_id}/result` 回报执行结果

**当前状态语义：**

- `gateway` 目标返回 `succeeded`：表示网关已本地应用配置
- `wristband / equipment / env` 目标返回 `succeeded`：表示网关已成功发布到局域网 MQTT
- 设备侧当前**没有预留 ACK 机制**，后台无法确认设备是否已实际应用或持久化配置
- 命令状态当前支持：`pending`、`succeeded`、`failed`、`timed_out`
- 网关每次成功拉取命令时，后台会递增 `attempt_count` 并设置短期 `leased_until`
- 网关回报 `failed` 时，如未达到 `max_attempts` 且未超过 `expires_at`，后台会按 `retry_backoff_s` 重新进入 `pending`
- 命令超过尝试次数时结束为 `failed`；超过有效期时结束为 `timed_out`

**手环配置示例：**

```json
{
  "ts": 1712345678,
  "hr_alert_threshold_high": 180,
  "hr_alert_threshold_low": 40,
  "notify_interval_ms": 100,
  "fall_detect_enabled": true
}
```

**器材配置示例：**

```json
{
  "ts": 1712345678,
  "notify_interval_ms": 500,
  "target_reps": 15,
  "power_limit_w": 500
}
```

**环境配置示例：**

```json
{
  "ts": 1712345678,
  "telemetry_interval_s": 30,
  "co2_threshold_ppm": 1000,
  "pm25_threshold_ugm3": 75
}
```

**网关配置示例：**

```json
{
  "ts": 1712345678,
  "gateway_id": "gw-001",
  "batch_interval_s": 10,
  "backend_base_url": "https://api.example.com/api/v1",
  "alert_rules": {
    "EQ_OVERLOAD": {
      "enabled": true,
      "threshold_ratio": 1.5,
      "window_s": 5,
      "level": "warning"
    },
    "DEVICE_OFFLINE": {
      "enabled": true,
      "timeout_s": 30,
      "level": "warning"
    }
  }
}
```

**配置参数说明：**

| 参数 | 适用设备 | 类型 | 说明 |
|------|---------|------|------|
| `hr_alert_threshold_high` | 手环 | int | 心率高阈值（bpm），超过触发 P0 告警 |
| `hr_alert_threshold_low` | 手环 | int | 心率低阈值（bpm），低于触发 P0 告警 |
| `notify_interval_ms` | 手环/器材 | int | BLE Notify 周期（毫秒），支持动态调整 |
| `telemetry_interval_s` | 环境 | int | MQTT 上报周期（秒），支持动态调整 |
| `fall_detect_enabled` | 手环 | bool | 是否启用跌倒检测 |
| `target_reps` | 器材 | int | 目标重复次数 |
| `batch_interval_s` | 网关 | int | 网关批量 HTTP 上报周期（秒） |
| `backend_base_url` | 网关 | string | 后台批量入库 API 基础地址 |
| `alert_rules` | 网关 | object | 网关 P1 规则配置，结构与 `rules.yaml` 对齐 |

**配置持久化：** 设备收到 config 后应持久化存储（Flash），断电重启后仍生效。

- 当前版本 `/api/ws/ops` 不强制要求 token，后续如接入统一鉴权，将由上层网关或反向代理控制。

### 3.10 数据入库（内网专用，网关调用）

| 方法 | 路径 | 描述 |
|------|------|------|
| POST | `/ingest/batch` | 网关批量上传，`{"items":[...]}` |

**请求体示例：**

```json
{
  "gateway_id": "gw-001",
  "sent_at": "2026-04-14T15:30:00Z",
  "items": [
    {
      "kind": "telemetry",
      "topic": "gym/gym-gz-01/equipment/eq-001/telemetry",
      "payload": {
        "ts": 1712345678,
        "gateway_received_ts": 1712345679,
        "device_id": "eq-001",
        "power_w": 350.5
      }
    },
    {
      "kind": "binding",
      "topic": "gym/gym-gz-01/wristband/wb-001/binding",
      "payload": {
        "ts": 1712345679,
        "wristband_id": "wb-001",
        "equipment_id": "eq-001",
        "action": "bind",
        "reason": "ble_connected"
      }
    }
  ]
}
```

**`kind` 枚举：**

| 值 | 含义 |
|----|------|
| `telemetry` | 遥测数据 |
| `alert` | 告警事件 |
| `binding` | 手环绑定 / 解绑事件 |
| `status` | 设备状态变更 |

## 4. WebSocket 消息格式

**业务端点：** `wss://{host}/api/ws?token={access_token}`
**运维端点：** `wss://{host}/api/ws/ops`
**协议：** JSON 文本帧  
**心跳：** 客户端每 30 s 发送 `{"type":"ping"}`，服务端回复 `{"type":"pong"}`  

**认证边界：**
- 目标协议仍为 `wss://{host}/api/ws?token={access_token}`
- 运维观测页面使用 `wss://{host}/api/ws/ops`
- 后台业务 WebSocket `/api/ws` 与后台自观测 WebSocket `/ops/ws` 在部署默认配置下都要求携带 `token={access_token}`
- `ops_observer` 对网页端暴露的 `/api/ws/ops` 当前仍不强制要求 token
- RTOS 设备端不直接连接该 WebSocket，WebSocket 面向前端页面与上层应用
**断线重连：** 客户端自行实现，指数退避（1 s → 2 s → 4 s，最长 30 s）

### 4.1 消息通用结构

```json
{
  "type": "<消息类型>",
  "data": { }
}
```

### 4.2 服务端 → 客户端（推送）

## 5. 模块通信总表

| 来源 | 目标 | 协议 | 说明 |
|------|------|------|------|
| 手环端 | 器材端 | BLE GATT | 手环遥测、时间同步、绑定信息 |
| 器材端 | 网关端 | MQTT | 器材遥测、手环转发、绑定、告警、状态 |
| 环境端 | 网关端 | MQTT | 环境遥测、告警、状态 |
| 网关端 | 后台端 | HTTP REST | 批量入库、命令结果回报 |
| 后台端 | 网关端 | HTTP REST | 配置建单后由网关轮询拉取 |
| 后台端 | 网页端 | REST + WebSocket | 业务查询、实时数据、告警 |
| 网关端 | 运维观测端 | REST + WebSocket | 健康、组件明细、运行统计 |
| 后台端 | 运维观测端 | REST + WebSocket | 健康、组件明细、运行统计 |
| 运维观测端 | 网页端 | REST + WebSocket | 健康中心、运维告警、统计聚合 |

> 约束：运维观测端不直接访问 PostgreSQL、Redis、InfluxDB、Mosquitto 私有协议。
