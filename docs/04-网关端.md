# 04 — 网关端

## 定位

部署于健身房本地的边缘计算节点，承担 MQTT 代理、边缘实时处理与 P1 异常告警功能。在网络断线时保障本地告警可用，在网络正常时将聚合数据转发至后台。

**BLE 接入已完全下移至器材端**，网关无需 BLE 硬件，只处理 MQTT 数据流。

---

## 1. 数据接收与转发

### 1.1 订阅来源

网关 MQTT Broker 接收以下设备上报的数据：

| Topic | 来源 |
|-------|------|
| `gym/+/wristband/+/telemetry` | 器材端（BLE Central 收到手环数据后转发） |
| `gym/+/wristband/+/binding` | 器材端（手环绑定 / 解绑事件） |
| `gym/+/equipment/+/telemetry` | 器材端（自身传感器数据） |
| `gym/+/equipment/+/alert` | 器材端 |
| `gym/+/equipment/+/status` | 器材端（上下线 / 状态变化） |
| `gym/+/env/+/telemetry` | 环境端 |
| `gym/+/env/+/alert` | 环境端 |
| `gym/+/env/+/status` | 环境端（上下线 / 状态变化） |

### 1.2 数据转发至后台

Edge Processor 聚合 10 s 内的数据，批量 HTTP POST 至后台 `/api/v1/ingest/batch`：

- 后台可达时：10 s 批量转发
- 上报内容统一包含 `telemetry`、`alert`、`binding`、`status`
- 后台不可达时：数据缓存至本地 InfluxDB 3 Core，恢复后补发
- 补发采用幂等策略（`ts` 字段唯一），后台 ON CONFLICT 忽略重复

### 1.2.1 时间语义与判定时间源

- `payload.ts` / `ts`：设备原始时间戳，由设备侧产生，进入网关后不得改写。
- `gateway_received_ts`：网关收到消息的本地时间，用于链路追踪、延迟分析和补发排序。
- `backend_received_at`：后台成功接收入库的时间，仅作为云端追踪辅助字段保留。
- 网关 P1 规则判断当前已支持统一配置项 `time_source`，可选 `payload_ts`、`gateway_received_ts`、`backend_received_at`。

> 当前默认仍使用 `payload.ts`。若切换到 `backend_received_at`，网关会优先读取 payload 中已存在的该字段；在网关本地尚未取得该字段时，回退使用 `gateway_received_ts`，以保持 P1 判断可执行。

### 1.2.2 当前实现路由结构

当前网关服务对外 HTTP 路由只有：

- `GET /healthz`
- `GET /ops/v1/health`
- `GET /ops/v1/health/components`
- `GET /ops/v1/stats`
- `WS /ops/ws`

实际主链路在 MQTT 与后台 HTTP 批量上传之间：

1. `edge_processor` 订阅 MQTT `telemetry / alert / binding / status`
2. 收到事件后先写入本地 InfluxDB 缓冲
   当前实现先进入进程内异步写入队列，再按批量写入 InfluxDB，避免 MQTT 消费协程被单条 HTTP 写入阻塞
3. 按批次调用后台 `POST /api/v1/ingest/batch`
4. 网关本地生成的 `alert` / `status` 也先写入缓冲，再发布到 MQTT
5. 网关周期性调用 `GET /api/v1/gateway/{gateway_id}/commands/pending`
6. 若命令目标是当前网关，则本地更新配置；若目标是器材端 / 环境端，则转发到局域网 MQTT `config` topic
7. 执行结果通过 `POST /api/v1/gateway/{gateway_id}/commands/{command_id}/result` 回报后台

### 1.2.3 运维观测接口（当前已实现）

为便于独立运维观测端统一查看每个网关节点的运行状态，网关当前已提供**自观测接口**，不再把健康汇聚职责放在业务后台：

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/ops/v1/health` | 返回网关整体健康摘要 |
| GET | `/ops/v1/health/components` | 返回组件级检查结果 |
| GET | `/ops/v1/stats` | 返回批量发送、缓存、命令执行等运行统计 |
| WS | `/ops/ws` | 向 `ops_observer` 推送实时状态变化（可选） |

认证约束：

- `GET /ops/v1/*`：当 `ops_auth.enforce_rest=true` 时，必须携带 `Authorization: Bearer {ops_token}`。
- `WS /ops/ws`：当 `ops_auth.enforce_ws=true` 时，必须携带 `?token={ops_token}`。
- 当前第 1 迭代本地部署默认启用上述鉴权，仅供 `ops_observer` 调用，不对网页端直接开放。

检查对象至少包括：

- `gateway_api`：网关 HTTP 健康接口
- `edge_processor`：边缘处理主服务
- `mqtt_broker`：Mosquitto
- `local_timeseries_db`：InfluxDB 3 Core
- `backend_api`：后台 `/healthz` 可达性

**当前实现边界：**

- 当前已实现：`GET /ops/v1/health`、`GET /ops/v1/health/components`、`GET /ops/v1/stats`、`WS /ops/ws`
- 代码中仍保留旧链路：`edge_processor -> POST /api/v1/system/health/report -> 后台`
- 正式迁移完成前，旧链路仅视为兼容实现，不再作为长期接口基线

### 1.3 发布（下行指令）

|-------|------|

## 2. 边缘告警处理（P1）

网关负责 **P1 低风险告警**的边缘判断与联动。P0 生命安全告警（心率异常、跌倒）由手环本地处理，网关收到后仅做联动记录，不重复判断。

### 2.1 P1 告警规则

| 告警码 | 触发条件 | 判断位置 | 联动动作 |
|--------|---------|---------|---------|
| `EQ_OVERLOAD` | 器材功率 > 额定功率 × 150% | 网关 Edge Processor | MQTT alert 发布 |
| `CO2_HIGH` | CO₂ > 阈值（默认 1000 ppm） | 网关 Edge Processor（或环境端本地） | MQTT alert，可联动新风系统 |
| `PM25_HIGH` | PM2.5 > 阈值（默认 75 µg/m³） | 网关 Edge Processor（或环境端本地） | MQTT alert |
| `TEMP_HIGH` | 温度 > 阈值（默认 35 °C） | 网关 Edge Processor（或环境端本地） | MQTT alert |
| `DEVICE_OFFLINE` | 30 s 未收到设备心跳 | 网关 Edge Processor | MQTT alert，后台标记设备离线 |

### 2.2 P0 告警联动

手环发出的 P0 告警（`HR_HIGH`、`HR_LOW`、`FALL_DETECTED`）经器材端 MQTT 转发至 Broker 后，网关 Edge Processor：

1. 转发至后台（入库）
2. 由后台统一通过 WebSocket 通知网页端（教练端实时告警）
3. **不重复判断**心率阈值（判断逻辑在手环本地）

### 2.3 告警规则动态调整

网关 Edge Processor 的 P1 告警规则支持**热加载**（无需重启容器）：

- **云控调整**：后台先写入配置命令，再由网关轮询拉取；若目标为当前网关，则 Edge Processor 本地改写 `rules.yaml` 并热重载
- **本地调整**：直接修改网关配置文件（YAML），Edge Processor 检测文件变更后自动重载
- 规则内容：各告警码的阈值、持续时间窗口、联动动作

### 2.4 告警规则配置文件格式（YAML）

Edge Processor 读取 `rules.yaml`，格式如下：

```yaml
# /runtime/config/edge_processor/rules.yaml
# 边缘处理服务启动时加载，文件变更后热加载（无需重启）

alert_rules:

  EQ_OVERLOAD:
    enabled: true
    description: "器材功率超额定功率比例"
    threshold_ratio: 1.5        # 超过额定功率 × 1.5 触发
    window_s: 5                 # 持续超标时间窗口（秒）
    level: warning
    action: mqtt_alert

  CO2_HIGH:
    enabled: true
    description: "CO₂浓度超标"
    threshold_ppm: 1000
    window_s: 60                # 持续 60 s 超标才告警（避免瞬时噪声）
    level: warning
    action: mqtt_alert

  CO2_CRITICAL:
    enabled: true
    description: "CO₂浓度严重超标"
    threshold_ppm: 1500
    window_s: 30
    level: critical
    action: mqtt_alert

  PM25_HIGH:
    enabled: true
    description: "PM2.5 超标"
    threshold_ugm3: 75
    window_s: 60
    level: warning
    action: mqtt_alert

  TEMP_HIGH:
    enabled: true
    description: "环境温度过高"
    threshold_c: 35.0
    window_s: 120
    level: warning
    action: mqtt_alert

  DEVICE_OFFLINE:
    enabled: true
    description: "设备心跳超时"
    timeout_s: 30               # 超过此时间未收到数据则判定离线
    level: warning
    action: mqtt_alert

# 全局参数
global:
  check_interval_s: 1           # 规则检查频率
  time_source: payload_ts       # payload_ts | gateway_received_ts | backend_received_at
  mqtt_alert_qos: 1
  log_level: info               # debug | info | warning | error
```

**热加载机制：** Edge Processor 使用文件监听（如 `watchdog` 库），检测到 `rules.yaml` 变更后，在当前规则检查周期结束时重新加载，不丢失进行中的时间窗口计数。

其中 `time_source` 当前默认使用 `payload_ts`，已支持切换到 `gateway_received_ts`；若选择 `backend_received_at`，在字段缺失时会回退到 `gateway_received_ts`。

## 3. 容器服务架构

### 3.1 Docker Compose 结构

```
docker-compose.yml
├── mosquitto       # MQTT Broker
├── edge-processor  # 边缘数据处理与告警
└── influxdb        # 本地时序数据库（边缘缓存）
```

所有服务配置 `restart: unless-stopped`，开机自动启动。

### 3.1.1 联调设备模拟器

为便于在 macOS + Apple `container` 和 Linux + Docker 环境下稳定复现 MQTT 联调场景，当前新增独立镜像：

- 模块目录：`gateway/device_simulator/`
- 部署目录：`deployment/gateway/device_simulator/`
- 镜像建议名：`motion-sense-device-simulator-local`

职责边界：

- 使用单个异步 Python 进程建立三组 MQTT 连接：`equipment`、`wristband`、`env`
- 默认模拟 `10` 台器材、`10` 个手环、`10` 个环境节点
- 发布 `telemetry`、`status`、`binding`，以及手环本地 P0 `alert`
- P1 场景优先通过异常 `telemetry` 触发网关规则，不直接伪造网关边缘告警

运行时文件：

- 首次启动自动生成 `/runtime/config/device_simulator/simulator_settings.yaml`
- 默认模板为 `default_simulator_settings.yaml`
- 修改模拟器配置需要重启容器

兼容说明：

- MQTT 用户名 / 密码当前默认使用开发联调值 `admin` / `admin123`
- 模拟器中手环 `current_equipment_id` 当前使用字符串设备 ID（如 `eq-001`），以兼容当前后台与网页端已实现链路

### 3.2 组件自初始化

每个容器在自身入口脚本中完成初始化，Docker Compose 只负责服务编排：

- `mosquitto`：若运行目录缺少正式配置，则从 `default_mosquitto.conf` 和 `default_acl.conf` 生成；若 TLS 证书或口令文件缺失，则拒绝启动并输出明确错误
- `edge-processor`：若运行目录缺少 `app_settings.yaml`、`rules.yaml`、`logging.yaml`，则从对应 `default_*` 模板生成
- `influxdb`：首次启动时生成运行时 `admin_token.txt`，随后检查 `gym_local` 数据库是否存在；不存在则创建并设置 7 天 retention period

运行目录由宿主机挂载，允许现场维护人员直接修改生成后的正式配置文件。

### 3.3 服务职责

#### Mosquitto（MQTT Broker）

- 接受来自器材端、环境端的 MQTT 连接（端口 1883 内网，8883 TLS）
- ACL 按 `gym_id + device_id` 隔离设备权限，设备只可向自己的 topic 发布
- 提供 WebSocket 端口（可选，供调试订阅）

#### 边缘处理服务（Python 3.13 异步服务）

核心功能：

| 功能 | 说明 |
|------|------|
| 数据入库 | 写入本地 InfluxDB 3 Core，按表分类存储 |
| P1 告警判断 | 订阅 telemetry → 阈值规则判断 → 发布 alert topic |
| P0 告警联动 | 收到手环 P0 alert → 转发后台，由后台 WebSocket 推送 |
| 数据批量转发 | 聚合 10 s 数据 → HTTP POST 至后台 |
| 离线缓存补发 | 后台不可达时缓存至 InfluxDB 3 Core，恢复后补发 |
| 设备心跳监控 | 30 s 未收到数据 → `DEVICE_OFFLINE` alert |
| 规则热加载 | 监听配置文件变更，实时更新告警规则 |
| 基础设施健康采集 | 周期检查网关本地关键组件，并通过 `/ops/v1/*` 或 `/ops/ws` 对外暴露 |

#### InfluxDB 3 Core（本地时序库）

- 本地使用数据库 `gym_local`，创建时设置 7 天 retention period
- 数据按 `telemetry`、`alert`、`binding`、`status` 表分类存储
- 后台断连时作为补发缓冲区
- 供 Edge Processor 查询聚合统计

### 3.4 热重载与重启规则

为避免运行时行为不确定，网关配置按以下规则生效：

| 文件 / 配置项 | 生效方式 |
|------|------|
| `rules.yaml` | **允许热重载**，Edge Processor 文件监听后自动生效 |
| `logging.yaml` | **允许热重载**，仅更新日志级别与输出格式 |
| `app_settings.yaml` | **需要重启 `edge-processor`**，涉及后端地址、批量上报间隔、并发参数 |
| `admin_token.txt` | **由 `influxdb` 首次启动自动生成**，`edge-processor` 从共享运行目录读取；若重建 Influx 数据目录，需同步保留或重新生成 |
| `mosquitto.conf` | **需要重启 `mosquitto`** |
| `acl.conf` | **需要重启 `mosquitto`** |
| TLS 证书 / 私钥 | **需要重启 `mosquitto`** |
| InfluxDB retention period | **需要重启 `influxdb`**，并按迁移流程处理已有数据 |

### 3.5 已知剩余风险

1. `mosquitto` 当前运行目录中的 `acl.conf` 由宿主机 bind mount 提供，在本地 Apple `container` 测试环境下会出现“文件属主与权限不属于 mosquitto 用户”的告警。
2. 当前 Mosquitto 2.1.2 仍可正常加载该文件并完成消息投递，但后续若升级到更严格版本，可能拒绝启动或拒绝加载 ACL。
3. 后续需要在 Linux 正式部署方案中补充宿主机文件权限初始化流程，确保 `acl.conf`、`passwd`、证书文件满足 broker 对属主与权限位的要求。

## 4. 平台选型

网关运行于本地 Linux 主机，通过 Docker Compose 管理所有服务。

| 项目 | 要求 |
|------|------|
| 平台架构 | ARM64 或 x86 均可 |
| 操作系统 | Linux（无桌面环境） |
| 运行时 | Docker + Docker Compose v2 |
| Edge Processor 语言 | Python 3.13（优先保证异步依赖稳定） |
| 边缘时序库 | InfluxDB 3 Core |
| 网络 | 有线以太网（优先）+ WiFi（备用） |
| 存储 | 系统盘 + 独立数据盘（提升时序数据 IOPS） |
| BLE 硬件 | **不需要**（BLE 接入已由器材端完成） |

## 5. 与后台连接流程

```
1. Docker Compose 启动全部服务（Mosquitto → InfluxDB → Edge Processor）
2. Edge Processor 连接本地 Mosquitto，订阅全部 telemetry / alert / binding / status topic
3. Edge Processor 尝试连接后台（HTTP 健康检查）
4. 后台可达：10 s 批量转发模式
   后台不可达：本地 InfluxDB 缓存模式，每 30 s 重试连接
5. 后台恢复后：读取 InfluxDB 缓存数据，分批补发至后台 /api/v1/ingest/batch
```

## 6. 当前阶段验证方式

以下验证方式面向当前第 1 迭代已落地实现，开发机基线为 macOS + Apple `container`。

1. 启动本地联调栈：

```bash
sh deployment/container/start_local_stack.sh
```

2. 发布一条器材遥测：

```bash
sh deployment/gateway/container/publish_sample_telemetry.sh \

```

3. 验证链路结果：
- `container logs edge_processor` 中应出现收到 MQTT 事件和批量上报日志
- 后台查询应能看到设备状态：

```bash

```

### 6.2 REST 批量上报验证

网关到后台主链路固定为 HTTP `POST /api/v1/ingest/batch`。联调时可直接检查后台接口结果：

```bash
curl http://127.0.0.1:18000/api/v1/telemetry/equipment/eq-001
```

预期：
- `telemetry` 主题进入对应历史查询接口
- `alert` 主题进入告警列表
- `binding` 主题进入绑定历史

### 6.3 本地缓存与补发验证

1. 暂停后台容器：

```bash
container stop backend
```

2. 再次发布 MQTT 遥测，确认 `edge_processor` 日志显示上报失败并保留缓存。
3. 恢复后台：

```bash
container start backend
```

4. 等待一个批量周期后验证后台接口：

```bash
curl http://127.0.0.1:18000/api/v1/telemetry/equipment/eq-001
```

预期：
- 后台恢复后能查到断连期间的缓存数据
- InfluxDB 补发成功后，对应事件不再出现在待补发结果中

### 6.4 规则热加载验证

1. 修改 `/runtime/config/edge_processor/rules.yaml`
2. 观察 `edge_processor` 日志，应出现规则文件变更检测日志
3. 发布触发阈值的 telemetry（例如环境 `co2_ppm` 持续超过阈值并达到 `window_s`）
4. 验证 Broker 上出现 `gym/{gym_id}/env/{node_id}/alert`，且后台 `GET /api/v1/alerts` 可查到对应 `P1` 告警

当前仓库已提供一键回归脚本：

```bash
sh deployment/gateway/container/verify_gateway_resilience.sh
```

该脚本会自动完成：
- 停止并重新拉起本地 `mosquitto`，验证网关自动重连后仍可将新遥测写入后台
- 临时下调 `CO2_HIGH.threshold_ppm` 与 `window_s`，等待热重载后验证新规则立即生效
- 退出前恢复 `rules.yaml`，避免污染后续联调环境

### 6.5 DEVICE_OFFLINE 验证

1. 确认 `rules.yaml` 中 `DEVICE_OFFLINE.enabled=true` 且 `timeout_s` 已配置（如 30）
2. 设备先发送一次 telemetry，随后停止发送超过 `timeout_s`
3. 订阅以下 topic 并观察：
   - `gym/{gym_id}/{device_type}/{device_id}/alert`
   - `gym/{gym_id}/{device_type}/{device_id}/status`（retained）
4. 预期：
   - 网关发布 `code=DEVICE_OFFLINE` 的 `P1` alert
   - 网关发布 `online=false,status=offline` 的 status
5. 设备恢复 telemetry 后，预期再次发布 `online=true,status=online` 的 status
当前 `edge_processor.app_settings.yaml` 与联调吞吐直接相关的 Influx 参数：

- `influxdb.write_queue_size`：进程内待写入队列容量，默认 `8192`
- `influxdb.write_batch_size`：单次落盘批量大小，默认 `256`
- `influxdb.replay_batch_size`：发往后台的补发批次大小，默认 `500`

这三项调整后都需要重启 `edge-processor`。
