# 04 — 网关端

## 定位

部署于健身房本地的边缘计算节点，承担 MQTT 代理、边缘实时处理与 P1 异常告警功能。在网络断线时保障本地告警可用，在网络正常时将聚合数据转发至后台。

**BLE 接入已完全下移至器材端**，网关无需 BLE 硬件，只处理 MQTT 数据流。

---

## 1. 数据接收与转发

### 1.1 订阅来源

网关 MQTT Broker 接收以下设备上报的数据：

| Topic | 来源 |
|-------|------|
| `gym/+/wristband/+/telemetry` | 器材端（BLE Central 收到手环数据后转发） |
| `gym/+/wristband/+/binding` | 器材端（手环绑定 / 解绑事件） |
| `gym/+/equipment/+/telemetry` | 器材端（自身传感器数据） |
| `gym/+/equipment/+/alert` | 器材端 |
| `gym/+/equipment/+/status` | 器材端（上下线 / 状态变化） |
| `gym/+/env/+/telemetry` | 环境端 |
| `gym/+/env/+/alert` | 环境端 |
| `gym/+/env/+/status` | 环境端（上下线 / 状态变化） |

### 1.2 数据转发至后台

Edge Processor 聚合 10 s 内的数据，批量 HTTP POST 至后台 `/api/v1/ingest/batch`：

- 后台可达时：10 s 批量转发
- 上报内容统一包含 `telemetry`、`alert`、`binding`、`status`
- 后台不可达时：数据缓存至本地 InfluxDB 3 Core，恢复后补发
- 补发采用幂等策略（`ts` 字段唯一），后台 ON CONFLICT 忽略重复

### 1.3 发布（下行指令）

| Topic | 用途 |
|-------|------|
| `gym/+/gateway/+/config` | 下发配置至网关 Edge Processor（P1 规则、批量上报参数） |
| `gym/+/equipment/+/config` | 下发配置至器材端（器材端再通过 BLE 转发至手环） |
| `gym/+/equipment/+/ota` | OTA 触发（器材端和手环） |
| `gym/+/env/+/config` | 下发配置至环境端 |
| `gym/+/env/+/ota` | OTA 触发（环境端） |

## 2. 边缘告警处理（P1）

网关负责 **P1 低风险告警**的边缘判断与联动。P0 生命安全告警（心率异常、跌倒）由手环本地处理，网关收到后仅做联动记录，不重复判断。

### 2.1 P1 告警规则

| 告警码 | 触发条件 | 判断位置 | 联动动作 |
|--------|---------|---------|---------|
| `EQ_OVERLOAD` | 器材功率 > 额定功率 × 150% | 网关 Edge Processor | MQTT alert 发布 |
| `CO2_HIGH` | CO₂ > 阈值（默认 1000 ppm） | 网关 Edge Processor（或环境端本地） | MQTT alert，可联动新风系统 |
| `PM25_HIGH` | PM2.5 > 阈值（默认 75 µg/m³） | 网关 Edge Processor（或环境端本地） | MQTT alert |
| `TEMP_HIGH` | 温度 > 阈值（默认 35 °C） | 网关 Edge Processor（或环境端本地） | MQTT alert |
| `DEVICE_OFFLINE` | 30 s 未收到设备心跳 | 网关 Edge Processor | MQTT alert，后台标记设备离线 |

### 2.2 P0 告警联动

手环发出的 P0 告警（`HR_HIGH`、`HR_LOW`、`FALL_DETECTED`）经器材端 MQTT 转发至 Broker 后，网关 Edge Processor：

1. 转发至后台（入库）
2. 由后台统一通过 WebSocket 通知网页端（教练端实时告警）
3. **不重复判断**心率阈值（判断逻辑在手环本地）

### 2.3 告警规则动态调整

网关 Edge Processor 的 P1 告警规则支持**热加载**（无需重启容器）：

- **云控调整**：后台通过 MQTT `gym/{gym_id}/gateway/{gateway_id}/config` 推送新规则至网关，Edge Processor 监听配置变更并实时生效
- **本地调整**：直接修改网关配置文件（YAML），Edge Processor 检测文件变更后自动重载
- 规则内容：各告警码的阈值、持续时间窗口、联动动作

### 2.4 告警规则配置文件格式（YAML）

Edge Processor 读取 `rules.yaml`，格式如下：

```yaml
# /runtime/config/edge_processor/rules.yaml
# Edge Processor 启动时加载，文件变更后热加载（无需重启）

alert_rules:

  EQ_OVERLOAD:
    enabled: true
    description: "器材功率超额定功率比例"
    threshold_ratio: 1.5        # 超过额定功率 × 1.5 触发
    window_s: 5                 # 持续超标时间窗口（秒）
    level: warning
    action: mqtt_alert

  CO2_HIGH:
    enabled: true
    description: "CO₂浓度超标"
    threshold_ppm: 1000
    window_s: 60                # 持续 60 s 超标才告警（避免瞬时噪声）
    level: warning
    action: mqtt_alert

  CO2_CRITICAL:
    enabled: true
    description: "CO₂浓度严重超标"
    threshold_ppm: 1500
    window_s: 30
    level: critical
    action: mqtt_alert

  PM25_HIGH:
    enabled: true
    description: "PM2.5 超标"
    threshold_ugm3: 75
    window_s: 60
    level: warning
    action: mqtt_alert

  TEMP_HIGH:
    enabled: true
    description: "环境温度过高"
    threshold_c: 35.0
    window_s: 120
    level: warning
    action: mqtt_alert

  DEVICE_OFFLINE:
    enabled: true
    description: "设备心跳超时"
    timeout_s: 30               # 超过此时间未收到数据则判定离线
    level: warning
    action: mqtt_alert

# 全局参数
global:
  check_interval_s: 1           # 规则检查频率
  mqtt_alert_qos: 1
  log_level: info               # debug | info | warning | error
```

**热加载机制：** Edge Processor 使用文件监听（如 `watchdog` 库），检测到 `rules.yaml` 变更后，在当前规则检查周期结束时重新加载，不丢失进行中的时间窗口计数。

## 3. 容器服务架构

### 3.1 Docker Compose 结构

```
docker-compose.yml
├── mosquitto       # MQTT Broker
├── edge-processor  # 边缘数据处理与告警
└── influxdb        # 本地时序数据库（边缘缓存）
```

所有服务配置 `restart: unless-stopped`，开机自动启动。

### 3.2 组件自初始化

每个容器在自身入口脚本中完成初始化，Docker Compose 只负责服务编排：

- `mosquitto`：若运行目录缺少正式配置，则从 `default_mosquitto.conf` 和 `default_acl.conf` 生成；若 TLS 证书或口令文件缺失，则拒绝启动并输出明确错误
- `edge-processor`：若运行目录缺少 `app_settings.yaml`、`rules.yaml`、`logging.yaml`，则从对应 `default_*` 模板生成
- `influxdb`：首次启动时检查 `gym_local` 数据库是否存在；不存在则创建并设置 7 天 retention period

运行目录由宿主机挂载，允许现场维护人员直接修改生成后的正式配置文件。

### 3.3 服务职责

#### Mosquitto（MQTT Broker）

- 接受来自器材端、环境端的 MQTT 连接（端口 1883 内网，8883 TLS）
- ACL 按 `gym_id + device_id` 隔离设备权限，设备只可向自己的 topic 发布
- 提供 WebSocket 端口（可选，供调试订阅）

#### Edge Processor（Python 3.13 异步服务）

核心功能：

| 功能 | 说明 |
|------|------|
| 数据入库 | 写入本地 InfluxDB 3 Core，按表分类存储 |
| P1 告警判断 | 订阅 telemetry → 阈值规则判断 → 发布 alert topic |
| P0 告警联动 | 收到手环 P0 alert → 转发后台，由后台 WebSocket 推送 |
| 数据批量转发 | 聚合 10 s 数据 → HTTP POST 至后台 |
| 离线缓存补发 | 后台不可达时缓存至 InfluxDB 3 Core，恢复后补发 |
| 设备心跳监控 | 30 s 未收到数据 → `DEVICE_OFFLINE` alert |
| 规则热加载 | 监听配置文件变更，实时更新告警规则 |

#### InfluxDB 3 Core（本地时序库）

- 本地使用数据库 `gym_local`，创建时设置 7 天 retention period
- 数据按 `telemetry`、`alert`、`binding`、`status` 表分类存储
- 后台断连时作为补发缓冲区
- 供 Edge Processor 查询聚合统计

### 3.4 热重载与重启规则

为避免运行时行为不确定，网关配置按以下规则生效：

| 文件 / 配置项 | 生效方式 |
|------|------|
| `rules.yaml` | **允许热重载**，Edge Processor 文件监听后自动生效 |
| `logging.yaml` | **允许热重载**，仅更新日志级别与输出格式 |
| `app_settings.yaml` | **需要重启 `edge-processor`**，涉及后端地址、批量上报间隔、并发参数 |
| `mosquitto.conf` | **需要重启 `mosquitto`** |
| `acl.conf` | **需要重启 `mosquitto`** |
| TLS 证书 / 私钥 | **需要重启 `mosquitto`** |
| InfluxDB retention period | **需要重启 `influxdb`**，并按迁移流程处理已有数据 |

### 3.5 已知剩余风险

1. `mosquitto` 当前运行目录中的 `acl.conf` 由宿主机 bind mount 提供，在本地 Apple `container` 测试环境下会出现“文件属主与权限不属于 mosquitto 用户”的告警。
2. 当前 Mosquitto 2.1.2 仍可正常加载该文件并完成消息投递，但后续若升级到更严格版本，可能拒绝启动或拒绝加载 ACL。
3. 后续需要在 Linux 正式部署方案中补充宿主机文件权限初始化流程，确保 `acl.conf`、`passwd`、证书文件满足 broker 对属主与权限位的要求。

## 4. 平台选型

网关运行于本地 Linux 主机，通过 Docker Compose 管理所有服务。

| 项目 | 要求 |
|------|------|
| 平台架构 | ARM64 或 x86 均可 |
| 操作系统 | Linux（无桌面环境） |
| 运行时 | Docker + Docker Compose v2 |
| Edge Processor 语言 | Python 3.13（优先保证异步依赖稳定） |
| 边缘时序库 | InfluxDB 3 Core |
| 网络 | 有线以太网（优先）+ WiFi（备用） |
| 存储 | 系统盘 + 独立数据盘（提升时序数据 IOPS） |
| BLE 硬件 | **不需要**（BLE 接入已由器材端完成） |

---

## 5. 与后台连接流程

```
1. Docker Compose 启动全部服务（Mosquitto → InfluxDB → Edge Processor）
2. Edge Processor 连接本地 Mosquitto，订阅全部 telemetry / alert / binding / status topic
3. Edge Processor 尝试连接后台（HTTP 健康检查）
4. 后台可达：10 s 批量转发模式
   后台不可达：本地 InfluxDB 缓存模式，每 30 s 重试连接
5. 后台恢复后：读取 InfluxDB 缓存数据，分批补发至后台 /api/v1/ingest/batch
```
